仓库已经加入初版本地 Web Demo 骨架：

- `apps/web`：React + TypeScript + Vite 三栏学习工作区
- `apps/backend`：FastAPI + SQLite 课程、资料、知识树、笔记版本和检索 API
- 当前可完成：创建课程、课程重命名与删除（右键菜单）、上传 PPTX、逐页解析、页面来源引用、知识点提取与**知识点关系（知识树）生成**、可编辑笔记、用户编辑保护和课程范围检索问答
- 当前上传格式限制为 PPTX；PDF、DOCX 解析器已预留目录，尚未接入
- Embedding 已提供 OpenAI-compatible 接口适配；未配置时使用本地关键词检索，配置后使用向量相似度混合检索
- DeepSeek 已提供结构化 JSON 提取和 RAG 回答适配；未配置 `DEEPSEEK_API_KEY` 时自动使用本地保守降级
- Electron 已建立安全桌面包装骨架，完整安装包和后端进程托管仍需下一阶段联调

### 本地启动

```powershell
cd apps/backend
uv sync
uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

另开一个终端：

```powershell
cd apps/web
npm install
npm run dev
```

浏览器打开 `http://127.0.0.1:5173`。本地课件和数据库写入根目录下的 `data/`，该目录不会提交到 Git。

> **端口说明**：后端的端口由根目录 `.env` 的 `NOTEBOOK_PORT` 决定（默认 8000），前端的代理目标会自动读同一个值。改了端口后前后端都会跟随，不需要改代码。

### 改了代码但界面没变化？

先跑一次自检：

```powershell
cd apps/backend
uv run python ../../scripts/check_backend.py
```

它会对比「正在运行的服务」与「磁盘上的代码」的路由表。如果出现类似输出：

```text
[X] 服务落后于代码！以下接口在代码里存在，但服务未注册：
  DELETE,PATCH   /api/v1/courses/{course_id}
```

说明**旧的后端进程仍占着端口**，你改的代码根本没被加载 —— 界面看起来就像"功能没实现"。按提示停掉占用端口的进程再重启后端即可。

（`uvicorn --reload` 在端口被上一个进程占用时不一定能干净重启，这是最容易踩的坑。）

### 大模型与检索配置

复制 `.env.example` 为根目录 `.env`，再填写配置。密钥只放在本地 `.env`，不要提交到 Git：

```text
DEEPSEEK_API_KEY=你的 DeepSeek API Key
DEEPSEEK_MODEL=deepseek-chat

# 可选：OpenAI-compatible Embedding 服务
EMBEDDING_BASE_URL=
EMBEDDING_API_KEY=
EMBEDDING_MODEL=
```

未配置 Embedding 时仍可使用关键词检索；要启用语义检索，需要同时填写三个 `EMBEDDING_*` 配置。笔记和回答以 Markdown 存储，数学公式使用 LaTeX，并由前端 KaTeX 渲染。

### 设置面板

左下角齿轮按钮打开设置抽屉，可查看当前能力状态（DeepSeek / Embedding 是否就绪、密钥写入是否开启、数据目录、上传上限、支持的格式），并直接修改模型名、服务地址、超时、上传上限，以及 **DeepSeek / Embedding 的 API Key**。所有输入框均为密码类型，输入内容不回显、不落日志。保存后立即生效、无需重启。

开启密钥写入：在 `.env` 中配置

```text
NOTEBOOK_ALLOW_SECRET_WRITE=true
NOTEBOOK_SETTINGS_TOKEN=你的自定义口令
```

重启后端后，在设置面板"设置口令"处填入相同口令即可保存密钥。安全约束：

- 状态接口只返回 `**** · 共 N 位`，**不泄露密钥任何真实字符**
- 写入新 Key 前先向服务端探活，**密钥无效直接拒绝，绝不覆盖仍然可用的旧 Key**
- 每次写入前自动备份 `.env` 到 `data/backups/`（仅保留最近 20 份），且写入时保留你的注释与手工配置
- 网络不可达时可设 `NOTEBOOK_SKIP_KEY_VERIFY=true` 跳过在线校验

密钥不会进入版本库：`.env` 与 `data/` 已被 `.gitignore` 忽略，仓库还启用了 `scripts/pre-commit` 钩子，会拦截误提交的 `.env`、本地数据和硬编码密钥。

### 课程重命名与删除

左侧课程卡片**右键**可打开操作菜单：

- **重命名**：只改课程名，课程下的资料、知识点、笔记全部保留
- **删除课程**：会一并删除该课程下的资料、解析页面、来源引用、检索块、知识点、笔记与版本历史，同时清理磁盘上的原始课件文件。为防误删，对话框要求完整输入课程名才能确认

删除后的提示条会显示实际清理了多少条记录。级联删除的完整性由 `apps/backend/tests/test_course_lifecycle.py` 覆盖。

详细架构见 [`docs/architecture.md`](docs/architecture.md)。

## 项目名称 Notebuddy
课程知识树 + 桌面答疑伙伴（工作代号）

---

## 一、背景与痛点

大学生在日常学习中普遍存在以下问题：

- **课件零散、无积累**：每门课的PPT一讲一讲地发，学期结束后往往是几十个独立文件，缺乏跨讲的知识关联，复习时无从下手。
- **AI笔记工具"用完即走"**：直接把PPT丢给大模型做摘要，只能处理单次、单份内容，无法识别"这个知识点之前讲过、这次是深化"，每次生成的内容互相割裂。
- **答疑资源不及时**：助教/老师答疑有时间和精力限制，学生遇到问题经常得不到及时反馈，尤其在深夜自习或考前冲刺时更明显。
- **学习工具普遍"反人性"**：纯管理型工具（笔记、待办）容易被束之高阁，缺乏持续打开使用的动力。

---

## 二、产品定位

一个**贯穿整个学期**的课程知识管理工具，包含两个核心部分：

1. **知识树笔记系统**：学生持续上传课程PPT，系统自动提取、摘要、去重、整合，生成一棵不断生长的、有设计感的**可视化知识树**，替代零散的笔记文件。
2. **桌面答疑伙伴**：一个常驻桌面的Electron挂件角色，基于学生自己的知识树内容做问答，点击/唤醒即可提问，随时获得贴合自己课程语境的解答。

**范围界定**：先做成通用框架（理论上适配任意课程），并用1门具体课程的真实PPT跑通完整demo进行验证。

**使用场景**：平时每周随讲积累 + 考前集中复习，两种场景贯穿使用。

**用户体系**：本阶段为单用户本地demo，不涉及登录注册和多用户系统。

---

## 三、核心功能设计

### 3.1 知识树笔记系统

| 功能 | 说明 |
|---|---|
| PPT结构化提取 | 不只提取文字，同时保留字体大小/加粗/层级等结构信息，作为判断"重点"的依据之一；提取时不需要还原/保留原PPT的字体样式，输出笔记的视觉呈现与原PPT无需一致 |
| 分级摘要 | 区分"核心概念"与"辅助细节"，而不是无差别地整段总结 |
| 跨讲增量整合 | 新上传的PPT会与历史内容做语义比对，判断是"全新知识点"还是"已有知识点的深化"，避免重复和割裂 |
| 来源索引标注 | 每条笔记内容标注对应原PPT的页码/位置索引，方便回溯核对，检查是否有内容遗漏 |
| 知识树可视化 | 将整理后的知识点组织成树状/网状结构展示，支持点击节点查看详情；自动生成为主，手动拖拽调整节点关系为加分项 |

### 3.2 桌面答疑伙伴

| 功能 | 说明 |
|---|---|
| 桌面常驻 | Electron实现的桌面挂件，角色可以"飘"在桌面上 |
| 被动唤醒交互 | 默认不主动打扰，点击/唤醒后才进入问答状态 |
| 基于知识树的问答 | 回答内容基于学生自己的课程知识库（检索增强生成），而不是泛泛的通用回答，保证贴合具体课程语境 |
| 答疑边界 | 本阶段只负责问答，不触发笔记整理或出题等任务，功能职责单一、清晰 |

## 四、技术方案

### 4.1 整体架构

```
[PPT文件] 
   → 结构化解析（文本 + 字体/层级信号）
   → 分级摘要（LLM：核心概念 / 细节）
   → 向量化（embedding）
   → 存入向量知识库（去重、增量整合）
   → 知识树数据结构生成
        ├─→ 前端可视化展示（网页/桌面端）
        └─→ 供桌面宠物问答时检索调用（RAG）
```

### 4.2 关键技术模块

- **PPT解析**：使用 `python-pptx` 提取文本内容及字体、加粗、层级等结构信息，作为重点判断的结构信号之一。
- **知识点结构化存储**：将提取内容整理为结构化记录（知识点名称、定义、所属章节、关联知识点、首次出现位置等），便于后续去重与关联展示，而非仅存储纯文本。
- **向量检索与知识库整合**：
  - 使用轻量级 embedding 模型 + 向量库（如 Chroma）实现语义检索
  - 新内容上传时先检索历史知识库中的相关片段，交由大模型判断"重复/深化/全新"，实现跨讲增量整合
  - 可参考开源RAG框架（如 Quivr 的 `quivr-core`）搭建基础检索问答流水线，减少重复造轮子的工作量
- **重点摘取**：结合结构信号（字体/加粗）+ 语义信号（LLM判断核心概念 vs 细节），输出分级摘要结果。
- **知识树可视化**：前端使用图/树状可视化方案（如 D3.js 或现成的思维导图库）渲染知识点关系，交互上支持点击查看详情、展开/收起节点。
- **桌面宠物壳子**：使用 Electron 搭建桌面常驻应用，前端展示角色动画与对话界面，后端调用同一套RAG检索问答逻辑。
- **大模型调用**：通过API接入大模型完成摘要生成、知识点结构化提取、问答生成等任务，核心工作量在于prompt设计与流程编排，而非自建模型。

### 4.3 技术栈一览

| 层级 | 选型 |
|---|---|
| PPT解析 | python-pptx |
| 向量检索 | 轻量级embedding模型 + Chroma（或参考Quivr的RAG流水线） |
| 结构化存储 | SQLite / PostgreSQL |
| 知识树前端 | Web前端（D3.js等可视化库） |
| 桌面宠物客户端 | Electron |
| 大模型能力 | 大模型API（摘要生成、结构化提取、问答） |

---

## 五、与"直接把PPT丢给大模型"的核心差异

1. **不是单次问答，而是持续积累**：知识库会随着每讲PPT的上传不断整合、去重、生长，形成整门课的知识体系，而非每次孤立生成一份摘要。
2. **重点判断有依据，不是纯粹依赖模型"感觉"**：结合PPT本身的结构信号（字体、层级）与语义分析，输出可解释的分级摘要。
3. **有一个持续陪伴的交互载体**：桌面宠物提供了一个轻量、低门槛的答疑入口，问答内容锚定在学生自己的课程语境里，而不是通用聊天。
